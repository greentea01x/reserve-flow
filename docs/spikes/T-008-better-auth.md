# T-008 — better-auth vertical spike

**Verdict: ADOPT WITH CAVEATS.** Every gate in the ticket was proven end to end against the
real PostgreSQL 18.6 in `infra/compose.yml` — 20 assertions, 0 failures. The `employee_code`
login path and the revocation guarantee both work and are *not* ugly. The caveats are three
config landmines and one feature better-auth simply does not have (remember-me 30 days).

Do **not** fall back to hand-rolled sessions.

## 1 · Table and column inventory better-auth owns

This is the authoritative answer for the schema freeze. It comes from
`getAuthTables(auth.$context.options)` — better-auth's own declaration, not a guess — with
the `modelName`/`fields` mapping from `src/auth/index.ts` applied.

`id` is implicit on every model and is **not** generated by better-auth: with
`advanced.database.generateId: false` the column is omitted from the INSERT and Postgres'
`gen_random_uuid()` DEFAULT supplies it. Proven: every row created in the spike got a
DB-side uuid.

### 2 · additionalFields

`auth.api.createUser` with `data: { employee_code, department_id, mobile, status }` writes
and reads back through better-auth's own output parser:

```json
createUser returned: { "name":"สมชาย ใจดี", "email":"somchai@example.co.th", "role":"ADMIN",
  "banned":false, "banReason":null, "banExpires":null,
  "employee_code":"EMP-0042", "department_id":"302703d1-…", "mobile":"0812345678",
  "status":"ACTIVE", "id":"61f13e3c-51c2-47eb-9479-3334dcd01915" }

row in postgres:  { …same values…, "failed_logins":0, "locked_until":null,
  "last_login_at":null, "disabled_at":null, "created_by":null }
```

`citext` works through the adapter: `WHERE employee_code = 'emp-0042'` matched the row
stored as `EMP-0042`.

Note the asymmetry in the API surface: `additionalFields` keep the key you declare
(`employee_code`), while core and plugin fields are returned camelCase (`banReason`)
regardless of the column name. Our API serializer must not just pass better-auth's object
through.

### 3 · employee_code login — the mechanism

**A thin resolve-code-to-email step, exactly as the spec (§07, BR-10) already decided.**
No custom credential provider, no plugin, no fork. ~4 lines:

```ts
const [row] = await db.select({ email: users.email })
  .from(users).where(sql`${users.employee_code} = ${identifier}`);   // citext, case-insensitive
await auth.api.signInEmail({ body: { email: row.email, password, rememberMe } });
```

Proven with `identifier = 'emp-0042'` — lowercase, hyphenated, categorically not an email —
resolving to `somchai@example.co.th` and signing in with HTTP 200 + a session row.

Two things T-012 must not forget, because better-auth cannot do them for us:
- when the identifier resolves to nothing, still burn a dummy `argon2.verify` before
  answering `401 INVALID_CREDENTIALS`, or the timing leaks which codes exist (§10.6 S-04);
- decide email-vs-code by `identifier.includes('@')` only for *logging*; always try the
  `employee_code` lookup and the `email` lookup, never branch the authentication itself.

The rejected alternative is worth naming: better-auth ships a `username` plugin that would
give a native second identifier, but it adds its own `username` + `display_username`
columns and a second uniqueness domain to keep in sync with `employee_code`. Two columns
and a sync problem to avoid four lines. Not worth it.

### 4 · Password hashing

`emailAndPassword.password.{hash,verify}` cleanly replaces better-auth's scrypt default.
The stored hash, read straight out of `accounts.password`:

```
$argon2id$v=19$m=65536,t=3,p=1$WZqeXdF9VbQAlH9MveZXxQ$WX+id69iu9OLous2DLnGHou4QA1EWmGboaS0bi93jNU
```

m=64 MiB, t=3, p=1 — matches §10.6 S-03. The override is honoured on **every** path that
hashes: `admin/create-user`, `admin/set-user-password`, and `ctx.password.hash` used by our
own set-password redeem (§7 below produced the same prefix).

### 5 · Cookie and session

The literal `Set-Cookie` emitted by `auth.api.signInEmail`:

```
__Host-sid=fLiauJrXCKF2XPKWgdVeTjNCryE1DUIo.IUJ7T%2FWnLajT3LXJo%2FtzrFKsFVmhc9M0pxYl7by7JNk%3D; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
```

`__Host-` prefix, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain` — all five
requirements met. It is the only cookie set.

Getting the name right is **not** obvious and is caveat Δ5: better-auth prepends
`__Secure-` to every cookie whenever it decides cookies are secure, so the naive
`cookies: { session_token: { name: '__Host-sid' } }` yields `__Secure-__Host-sid`. The
working combination is

```ts
advanced: {
  useSecureCookies: false,                     // suppress the automatic __Secure- prefix
  defaultCookieAttributes: { secure: true, httpOnly: true, sameSite: 'lax', path: '/' },
  cookies: { session_token: { name: '__Host-sid' } },
}
```

`useSecureCookies: false` is a misleading name here — the attributes block re-asserts
`Secure` on every cookie, so nothing is actually downgraded. Leave the comment in place.

The matching `sessions` row (note `ip_address`/`user_agent` populated from the request):

```json
{ "id":"d6ad744e-…", "user_id":"cfac99a0-…", "token":"fLiauJrXCKF2XPKWgdVeTjNCryE1DUIo",
  "expires_at":"2026-08-30T23:26:44.387Z", "ip_address":"10.1.2.3",
  "user_agent":"spike/1.0", "impersonated_by":null }
```

The cookie value is `token.hmac`; the `sessions.token` column stores only the token half.

### 6 · Deactivation

Three separate results, and the order matters:

**6a — `banned = true` alone does NOT revoke a live session.** The admin plugin only checks
`banned` in `databaseHooks.session.create.before`, i.e. at sign-in. A session created before
the ban keeps working: `auth.api.getSession()` returned a valid session *after* the user was
set `banned=true, status='DISABLED', disabled_at=now()`. If anyone implements deactivate as
"flip the flag", the user stays logged in for up to seven days.

**6b — deleting the session rows revokes on the very next request.** Same cookie, same
`getSession` call, `null`. This is the guarantee the spec asks for and it is exact: there is
no cookie cache in front of it (`session.cookieCache` is off by default and must stay off).

**6c — sign-in afterwards is refused** with `403 BANNED_USER`, which our wrapper maps to
`403 ACCOUNT_DISABLED`.

**6d — `auth.api.banUser` is unusable against the spec DDL.** It updates `banned` and
`ban_reason` without touching `status`/`disabled_at`, so Postgres rejects it:

```
23514 users_banned_mirror — new row for relation "users" violates check constraint "users_banned_mirror"
```

This is the constraint doing its job. `POST /admin/users/:id/deactivate` must be ours: one
transaction that sets `status='DISABLED', banned=true, disabled_at=now()`, deletes the
user's `sessions` rows, cancels their future bookings, and writes the audit row. Never call
`auth.api.banUser` / `unbanUser`; add both to the 404 list in §07 alongside the other
better-auth routes.

Belt and braces, per §10.6 S-01: our `requireAuth` middleware should still join
`users.status` on every request, so a session that somehow survives is rejected anyway.

### 7 · Invite / set-password token

Everything works, and better-auth's own reset-password machinery stays unused as D-29/C2-06
decided.

- **7a** `auth.api.createUser` **without** a `password` creates the user and **zero**
  `accounts` rows. That is the "no usable password" state — cleaner than a random password,
  because there is nothing to brute-force.
- **7b** Sign-in before redeem: `401`.
- **7c** Redeem is a single `UPDATE … WHERE token_hash = $1 AND used_at IS NULL AND
  expires_at > now() RETURNING …` inside one transaction. First call `redeemed`, second call
  `TOKEN_EXPIRED`. The single-use guarantee is the `WHERE used_at IS NULL` on the UPDATE, not
  a read-then-write — no race.
- **7d** After redeem the user signs in (`200`) and the hash written by *our* path is also
  `$argon2id$v=19$m=65536,…`, because the redeem uses `auth.$context.password.hash`.
- **7e/7f** No unused tokens survive; only `sha256(token)` is stored, the plaintext exists
  only in the email.

**TTL knobs are ours, in `password_setup_tokens.expires_at`** — the app sets
`now() + 7d` for `INVITE` and `now() + 24h` for `RESET`/`FORGOT`. better-auth's
`emailAndPassword.resetPasswordTokenExpiresIn` is a single system-wide value and is not
used. **Storage table: `password_setup_tokens` (ours). Not `verifications`.**

The redeem writes account + `users.status='ACTIVE'` + `email_verified=true` + `DELETE FROM
sessions` in one transaction; T-012 adds the outbox insert to the same transaction, which is
the whole reason C2-06 rejected better-auth's callback-based reset.

Set-password cannot go through `auth.api.setUserPassword`: that endpoint requires an
authenticated admin session, and the person redeeming an invite has none. Use
`auth.$context.internalAdapter` (or plain SQL, as the spike does) with
`issuer = createLocalAccountIssuer('credential')`.

### 8 · Rate limiting and lockout

| Need | better-auth gives | We must build |
|---|---|---|
| Per-IP/route request limit | Yes, but **only on `auth.handler`** (`/api/auth/*`) and **off outside production** by default. Enabled with `max: 5, window: 60` the HTTP path returned `401,401,401,401,401,429,429,429,429,429`. | Everything, because §07 C-13 404s `/api/auth/*` and we call `auth.api.*` in-process. |
| In-process calls | **Nothing.** 10 consecutive `auth.api.signInEmail` calls with a wrong password: `401 ×10`, no 429. | `hono-rate-limiter` on our wrapper routes: sign-in 5/min per IP+identifier, `/auth/forgot` 3/h per identifier + 10/h per IP. |
| Per-account lockout | **Nothing.** `failed_logins` stayed `0` and `locked_until` `null` after 20 failed attempts. | The whole of it: increment `failed_logins`, set `locked_until = now() + 15 min` at 5, answer `423 ACCOUNT_LOCKED`, reset on success alongside `last_login_at`. |

Recommendation: leave `rateLimit.enabled: false` (the knob exists in `createAuth` only so
this spike could demonstrate the native behaviour) and put every limit on our own routes.
One limiter in one place beats two that disagree.

## 3 · Changes §06 needs (schema freeze input)

| Δ | Where | Change |
|---|---|---|
| **Δ1** | §6.2 `accounts` | Add `issuer text NOT NULL` and `CREATE UNIQUE INDEX accounts_issuer_account_id_idx ON accounts (issuer, account_id)`. Required by better-auth 1.7; without it the adapter throws. Credential rows carry `issuer='local:credential'`. |
| **Δ2** | §6.11 better-auth config | The admin plugin's fields carry no `fieldName`, so they resolve to columns literally named `banReason`, `banExpires`, `impersonatedBy`. Either rename those three columns, or keep snake_case and add the mapping — we chose the mapping: `admin({ schema: { user: { fields: { banReason: 'ban_reason', banExpires: 'ban_expires' } }, session: { fields: { impersonatedBy: 'impersonated_by' } } } })`. Losing this line breaks ban/unban with a raw Drizzle error. |
| **Δ3** | §6.2 `users` + §07 | `users_banned_mirror` makes `auth.api.banUser`/`unbanUser` fail with `23514`. Keep the CHECK; add both endpoints to the better-auth routes §07 already 404s, and make `POST /admin/users/:id/deactivate` the only writer of `banned`. |
| **Δ4** | §6.2 preamble + §6.11 `0000_extensions_and_functions.sql` | **`CREATE EXTENSION citext` fails as `rf_owner`: `42501 — must have CREATE privilege on current database`.** The spec's claim that trusted extensions need no superuser is true in general but false under our role grants: `infra/db/init/01-roles.sql` gives `rf_owner` CREATE on *schema* `public` only, and revokes CREATE on the database from PUBLIC. Fix by adding `create extension if not exists citext;` next to the existing `btree_gist` line in `infra/db/init/01-roles.sql` (runs as the bootstrap superuser), and drop both `CREATE EXTENSION` lines from `0000_…sql` — or grant `CREATE ON DATABASE reserveflow TO rf_owner`. The first is smaller and keeps `rf_owner` unprivileged. `btree_gist` has the same problem and only works today because the init script already creates it. **Applied**: `infra/db/init/01-roles.sql` now creates `citext` next to `btree_gist`. |
| **Δ10** | §6.11 `0006_grants.sql` | Spotted while granting for the spike: `01-roles.sql` already does `alter default privileges for role rf_owner … grant select, insert, update, delete on tables to rf_app`, so every table T-009 creates arrives with `DELETE` for `rf_app` — the opposite of §10.6's "no DELETE by default, DELETE per table". `0006_grants.sql` must `REVOKE` it back, or the default-privileges line must lose `delete`. Not an auth issue, but it lands in the same migration wave. |
| **Δ5** | §6.11 / §10.6 S-01 | Document the cookie recipe: `useSecureCookies: false` + `defaultCookieAttributes.secure: true` + `cookies.session_token.name`. The obvious spelling produces `__Secure-__Host-sid`. |
| **Δ6** | §07 C-03, BR-10 | **"Remember me = 30 days" is not achievable with better-auth's public API.** `rememberMe: true` yields `Max-Age = session.expiresIn` (604800 = 7 d); `rememberMe: false` yields a browser-session cookie with the same 7-day DB row. There is no per-sign-in expiry override. Either redefine remember-me as "stay signed in after closing the browser" (free, already works, recommended), or T-012 adds a post-sign-in `UPDATE sessions SET expires_at = now() + 30 days` plus a re-issued cookie — extra code on the hottest path for a nice-to-have. |
| **Δ7** | §6.11 config list | `admin({ adminRoles: ['ADMIN'] })` alone is not enough: the constructor validates role names case-insensitively but `hasPermission` looks them up by exact key, so every admin endpoint answers *"You are not allowed to …"*. Needs `roles: { ADMIN: adminAc, EMPLOYEE: userAc, FACILITY: userAc }` from `better-auth/plugins/admin/access`. |
| **Δ8** | §6.2 `users` | Informational: better-auth declares `role` and `banned` as nullable with `input:false`; the spec's `NOT NULL DEFAULT` is stricter and works, because the plugin's create hook always supplies `defaultRole`. No change needed — do not "fix" it to match the library. |
| **Δ9** | §6.2 `sessions` | Informational: `expires_at` is an absolute timestamp; sliding comes from `session.updateAge` (set to 24 h), which rewrites the row when a session is used and is older than that. `session.cookieCache` must stay **off** or 6b's immediate-revocation guarantee is lost. |

Nothing in `bookings`, `notifications`, or `audit_logs` is affected. `password_setup_tokens`
as specced in §6.2 is correct exactly as written.

## 4 · Recommendation

**Adopt better-auth 1.7.1.** It earns its place: Postgres-backed sessions we can delete,
argon2id we control, the four admin columns, `createUser` with no password, and a
`getSession` we can trust. The hand-rolled fallback would buy nothing that is currently
broken and would cost us the session/account plumbing.

The caveats are all *configuration*, all now encoded in `apps/api/src/auth/index.ts`, and
all have a comment saying why. The one genuine capability gap is remember-me-30-days (Δ6),
and the cheapest resolution is to redefine the requirement rather than write code.

What T-012 owns, none of which better-auth provides: the identifier→email resolve, the
dummy-hash timing defence, `failed_logins`/`locked_until` lockout, rate limits on our own
routes, the deactivate transaction, and the `password_setup_tokens` flow.
