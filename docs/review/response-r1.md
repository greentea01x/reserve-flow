## Amendments to DECISIONS

These are the deltas against `work/DECISIONS.md`. The same list has been appended to that file under `## Amendments (Codex round 1)`.

1. **Jobs — pg-boss dropped** (C1-37). §C "Jobs" now reads: in-process `jobs/scheduler.ts` (~40 lines), `setInterval` + `pg_try_advisory_xact_lock` per job + `stop()` on SIGTERM; `booking.sweep` 60 s, `notify.send` 10 s + post-commit kick, `maintenance.daily` 03:15; `/readyz` exposes `last_sweep_at`. No `pgboss.*` schema, no second retry model.
2. **PostgreSQL 18 kept, but pinned and mounted correctly** (C1-03, C1-39). Volume is `pgdata:/var/lib/postgresql` (PG18 moved `PGDATA` to `/var/lib/postgresql/18/docker`); image is `postgres:18.1-alpine@sha256:<digest>`, the identical pin in compose, CI service, staging and prod. Codex's "use 17 instead" is not adopted — the fix removes the reason to downgrade.
3. **CSRF is our own middleware, not Hono `csrf()`** (C1-12). Every unsafe method, any content type or none, must carry `Origin ∈ [PUBLIC_BASE_URL] ∪ CSRF_EXTRA_ORIGINS` or `Sec-Fetch-Site: same-origin`. New env `CSRF_EXTRA_ORIGINS` (empty in prod, `http://localhost:5174` locally for the admin dev server).
4. **`BETTER_AUTH_SECRET` is a required managed secret** (C1-02) — ≥32 random bytes, zod-checked at boot, distinct per environment, never generated at container start, in the rotation runbook. It was absent from §C entirely.
5. **Canonical account state = `users.status`; `banned` is a DB-enforced mirror** (C1-17). `CHECK (banned = (status='DISABLED'))`; session revocation is a direct `DELETE FROM sessions` on the same tx client. better-auth is confirmed only after the **W0 T-008 vertical spike gate**, which now blocks schema freeze; the ~150-line hand-rolled fallback becomes a W0 decision, not a mid-W1 escape.
6. **Employee identity boundary** (C1-20). `email_verified` is set true only on invite redemption, never at admin creation; new env `ACCOUNT_EMAIL_DOMAINS` restricts account creation **and CSV import** to the company domain (422 otherwise). External attendee addresses stay contacts without `user_id`.
7. **AUTO_RELEASED now cancels attendee calendars** (C1-14). §B email events: `AUTO_RELEASED` = owner + admins (explanatory mail) **plus every original calendar recipient with `.ics METHOD:CANCEL`, same UID, `SEQUENCE=version`**. Previously "owner + admins", no attendee `.ics`.
8. **Check-in / operational policy is retroactive by design** (C1-15). §B's "master-data changes apply to new requests only" now holds for booking-window rules **only**. `checkin_open_before_minutes`, `checkin_grace_minutes`, `auto_release_enabled`, `reminder_minutes_before` read current values every sweep and therefore apply immediately to all live bookings; the Settings screen must state this. New cross-field rule `1 ≤ checkin_grace_minutes < min_duration_minutes`. Settings storage stays key/value JSONB, validated as a whole document by zod (no typed `booking_policy` table, no per-booking policy snapshot).
9. **Idempotency storage stays on the `bookings` row — with a fixed claim order** (C1-08). No separate idempotency table. Order inside T1: `pg_advisory_xact_lock(hashtext(actor‖':'‖key))` → replay `SELECT` → return the existing booking **before** any room lock or H1 sweep → only then room lock/insert. `UNIQUE (created_by, idempotency_key)` remains the second net. Same key + different payload deliberately returns the original booking (the key binds to one submit, not to a payload).
10. **Approval order is canonical and lock-revalidated** (C1-04, C1-09). Everywhere: read target → advisory lock room → re-read `FOR UPDATE` and compare room/range/status/version (difference ⇒ rollback + one retry from the new room) → reject directly-overlapping pendings → confirm winner → audit/outbox. A failed winner update rolls back the loser rejections.
11. **Conflict group ≠ rejection set** (C1-25). A connected component is a display container only; approving a request rejects only the pendings that overlap it **directly** (`conflicts_with[]`). §B's "losers auto-rejected" is scoped accordingly.
12. **Attendee edits are optimistically locked** (C1-13, C1-28). `PUT /bookings/:id/attendees` requires `version` and obeys the same predicate as PATCH; bookings become uneditable at `CHECKED_IN` (admin cancel only). §B's "detail-only edits never re-approve" is unchanged.
13. **Staffing baselines replace "1 lead + 1–2 devs / W8 buffer"** (C1-06). Net capacity ≈32 h/dev/week (80 % focus); MVP W0–W6 ≈568 h. **3 devs ⇒ W8 go-live (the baseline for the 8-week date)**; 2 devs ⇒ W10–W11, or W8 only with the pre-approved cut list; 1 dev ⇒ W18–W20. W8 is go-live/hypercare, **not** development buffer.
14. **Scope gates** (C1-22). Utilization per room/month is not a cut candidate before heatmap/outcomes. Admin drag-and-drop stays in 1.1 **only with a written waiver** from the requirement owner in W0; otherwise T-102 enters W6 and requires the third dev.
15. **Retention adds booking free-text scrubbing** (C1-19). §C security baseline gains: booking `title`/`description`/`special_request`/`reason` scrubbed at 24 months (statistical facts retained); retained-identifier cases are **pseudonymisation**, not anonymisation; a field-level PII inventory + DSAR + breach runbook is owned by company HR/DPO and confirmed in W0.
16. **Staging and restore drills separated from production data** (C1-21). §C "quarterly restore drill into staging with PII scrub" is replaced by: staging carries seed/test data only and never a production dump; restores run in an isolated `rf-drill` compose project (no Caddy route, no published ports) with `scrub-drill.sql` in one transaction **before any service starts**, then `down -v`; annual bare-VM restore as DR proof. Staging still shares the production VM.
17. **Email SLO restated** (C1-18). NFR-5 "delivery > 99 %" now means **relay accepted ÷ attempted**, invalid addresses excluded, with bounce monitoring on `MAIL_FROM` — explicitly not inbox delivery — and requires written business acceptance. The real relay path is proven in W0 (T-009), not W7.

## Still open / deliberately rejected

**Rejected outright**

- **C1-38 — one Vite app instead of two SPAs.** We keep two. The admin bundle (dnd-kit, reports, user management) never reaching 80 employee browsers is a real, measurable benefit, and the two shells differ structurally (bottom tabs vs sidebar), so "lazy `/admin/*` chunks" would still need two layout trees. Codex's actual defect — the false claim of independent release cadence — is fixed by stating that both apps ship in one image tag and by consolidating the duplicated bootstrap into `packages/ui`/`packages/shared`. The single-app option is documented as a low-cost W1 reversal if the team disagrees.

**Accepted risks, deliberately narrower than requested**

- **C1-08 — no request hash.** An `idempotency_requests` table with `request_hash` buys `409 IDEMPOTENCY_KEY_REUSED` for a case that cannot occur in our client: the key is minted per submit-button press and never reused with a different body. The actual defect (H1 running before the replay check) is fixed by ordering, and `UNIQUE (created_by, idempotency_key)` is the backstop. Revisit if a third-party client ever gets an API token.
- **C1-15 — settings stay JSONB.** One `PUT` validates the whole document with cross-field zod rules, which gives the same guarantees as DB CHECKs for a single-writer admin screen at a fraction of the migration cost. Per-booking policy snapshots are rejected outright: with 3 rooms and one operations policy, snapshotting would mean live bookings silently running different grace periods, which is harder to explain to an admin than "changing grace affects today's meetings" — which we now say on the screen. The one genuinely dangerous interaction (grace ≥ meeting length) is blocked by `grace < min_duration_minutes`.
- **C1-16 — pending rows are masked, not aggregated.** Unrelated employees get `BUSY` (id/room/time/status) instead of an aggregate. The identifiers are already derivable from the calendar feed, and per-slot rows are what the grid renders; aggregating would need a second query shape for one privacy nuance that the masking already covers (no title, owner, department or attendee count).
- **C1-17 — hand-rolled auth fallback retained.** Removed from the *middle* of W1, not from the plan: T-008 is a W0 gate that decides before `T-007` (schema) merges, so we never carry two auth designs into the schema. Company OIDC remains preferable and stays Q-08/Phase 2 — it is an IT-availability question, not ours to decide.
- **C1-21 — staging still shares the production VM.** The PII exposure Codex identified is closed (no production dump on staging, restores isolated in `rf-drill` with scrub-before-start, Mailpit behind basic-auth with a "no real data" rule). A permanently separate staging VM costs money every month to solve a problem the data policy already solves.
- **C1-30 — no capacity-facts table.** Business hours change roughly once a year for this company; storing daily capacity facts or effective-dated policy would add a table and a backfill to make a report immune to an event that has never happened. Mitigated by printing "calculated with current business hours" on the report and by monthly CSV export as the snapshot. `ponytail:` note names the upgrade trigger.
- **C1-31 — no lease/`SENDING` state in the outbox.** At ~30 messages/day on a single API instance, the failure window is one duplicate email after a crash mid-send, and a deterministic `Message-ID` lets the recipient's mailbox collapse it. A lease adds a state machine, a reclaim loop and an expiry knob to prevent something a mailbox already prevents. **Genuinely still open**: obsolete-event suppression is implemented only for reminders (status + `start_at` check before send); a stale CONFIRMED mail could still arrive after a newer CANCELLED one if the relay was down between them. Cheap follow-up if it ever shows up in UAT: extend the pre-send check to compare `payload.version` with `bookings.version`.
- **C1-33 — no `/impact` endpoint and no `If-Match` on settings.** The impact preview now consumes every page of a bounded query (≤30 days × 3 rooms), so nothing is missed; a server-side endpoint would duplicate `validateWindow()` on the server for a warning banner. Settings lost updates need two admins editing the same document within seconds, which is not this company's failure mode. Both are one-ticket additions if the room count grows.
- **C1-36 — calendar budget is 24 h + a half-day prototype, not 5 days.** The prototype de-risks the part Codex was right about (nobody has seen the screen yet) and is scheduled in W1, two weeks before the ticket. **Still inconsistent**: ADR-007 says "~1 สัปดาห์ใน W2" while T-025 is XL (24 h) — one of the two numbers should be corrected in a follow-up pass.
- **C1-40 — FK indexes not added.** The grants half is done. Indexes on `decided_by`, `checked_in_by`, `cancelled_by`, `users.created_by` were **not** created; at ~5k bookings/year the sequential scans on user deactivation are milliseconds, but this is a 4-line migration and there is no argument for skipping it — it should simply be picked up.
